# 自定义系统（主题 / 布局 / 快捷键 / 命令 / 插件）

日期：2026-09-19 起。工具链：rustc 1.98.1。

---

## 1. 手改的 `config.json` 带 UTF-8 BOM，整份配置静默失效

* **现象**：把 `"theme"` 改成 `"dark"` 保存、重启，界面仍是浅色——像是主题没接上。
* **根因**：Windows 的记事本 / PowerShell `Set-Content -Encoding UTF8` 写文件会带
  UTF-8 BOM（`EF BB BF`），而 `serde_json` 从第一个字节就要是 JSON，遇到 BOM 直接
  报 `expected value at line 1 column 1`。`Config::load` 把错误吞成
  `unwrap_or_default()`，于是**整份配置**（主题、书签、标签）都回落默认值，
  用户看到的是「改了没反应」，而且没有任何提示。
* **修法**：`Config::load` 先按字节读、剥掉可选 BOM 再交给 `serde_json`
  （`crates/mo-config/src/lib.rs`），并加 `load_tolerates_utf8_bom` 回归测试。
* **教训**：凡是「指望用户手改」的配置文件，读取端必须按**最坏输入**设计：
  BOM、CRLF、缺字段（全部 `#[serde(default)]`）都要能活下来。静默回落默认值
  是最坏的失败模式——它把配置错误伪装成功能没做。

## 2. 主题不能从上下文取色：约 200 处调用点在 `div()` 链中间

* **现象**：把 `theme` 做成 `impl Global` 让调用方 `cx.global::<Theme>()` 取，
  改到 `file_list` / `toolbar` 就推不动了——大量取色发生在
  `.bg(theme::container())` 这种链式调用里，那里没有 `Window` / `App`。
* **根因**：gpui 的 `Div` 构造是纯值操作，取色时机在 render 函数体内，
  不是元素自己 request_layout 时——框架不会把上下文递到链式调用中间。
* **修法**：`mo_ui::theme` 保留自由函数签名（`text()` / `surface()` / …），
  内部读一份进程级 `Mutex<Palette>`；切主题 = 写这个槽位 + `cx.notify()`。
  渲染与按键都在应用线程，没有并发问题。
* **注意**：`gpui_component::Theme` 是**另一个**全局（框架组件自己的），
  `global_mut` 对它不存在时直接 panic。headless 测试只 `gpui::init` 过，
  没有这个全局——所以 `apply_component` 必须先 `try_global` 探测再写。

## 3. 深色主题下写死的浅色专用色会「局部回到浅色」

* **现象**：切深色后大部分界面正常，但 diff 视图的相同行是一片死白。
* **根因**：`diff_eq_bg()` 等 5 个 diff 配色是写死的浅色档常量，没走主题。
* **修法**：相同行底色改取 `theme::surface()`，增删两档按 `theme::is_dark()`
  给深色专用 tint（暗红 / 暗绿底 + 提亮的前景）。
* **教训**：接主题系统时不能只换「主面板四件套」，要按 `ROLES` 全表过一遍
  所有硬编码颜色；语义色（增/删/警示）在深色档需要单独一档，直接反色不可读。

## 4. 测试读到了开发者机器上的真实配置

* **现象**：布局偏好上线后，`mo-ui` 的 headless 测试在某台机器上失败（「文件列表没有渲染」），换台机器又好了。
* **根因**：`RootView::new` 会读 `config.json` 拿视图模式 / 侧边栏开关——这些偏好**会改变渲染结构**，测试于是依赖了开发者机器的私有状态；而 `AppState::config_path()` 写死系统配置目录，测试无从覆盖。
* **修法**：`MO_CONFIG_DIR` 环境变量可钉住配置目录（便携部署也认这个）；`mo_ui::isolate_config_for_tests()` 把它指到进程临时目录，所有会建 `AppState` 的测试开头调一次。
* **注意**：隔离目录是**整进程共享**的一份，所以测试里**不要写配置文件**——并发的测试会读到彼此写的内容，表现为随机失败。要测「配置 → 行为」就拆两段：配置解析用纯单测，行为用注入后的对象测。

## 5. 自定义快捷键：硬编码分支必须删干净

* **现象**：加了键表之后，用户把 `⌘T` 改绑到别处，`⌘T` 仍然会新建标签页。
* **根因**：键表只是「加了一层」，原来那些 `if platform && key.eq_ignore_ascii_case("t")` 硬编码分支还在按键路由里，先命中先执行。
* **修法**：把全局键位整段换成「查键表 → `dispatch_action(id)`」，硬编码分支全部删除；裸键（回车 / 空格 / Delete / F2）同样走键表，但**退格删过滤词、Esc 清过滤、方向键移动焦点、单字符输入即过滤**保留为结构性按键——它们不是「动作」，塞进键表反而会把「按退格删一个过滤字符」这种手感弄没。
* **注意**：解绑（配置里写空串）不能只是「不绑到动作」，还要**吞掉这次按键**，否则会漏给系统 / 输入组件触发别的行为；键表里为此单独记了一份 `unbound` 名单。

## 6. Windows 上「⌘快捷键」全都按不出来：gpui 的 platform 是 Win 键

* **现象**：用真实合成输入（Ctrl+T / Ctrl+Shift+P）在 Windows 上打不开命令面板、也不新建标签页——看起来像「快捷键功能压根没做」。
* **根因**：`gpui-pre-windows/src/events.rs` 里 `Modifiers.platform = VK_LWIN | VK_RWIN`，Ctrl 落在 `control`。而全局快捷键一律写成 `if platform && key == "t"`——在 Windows 上等于要求用户按 **Win+T**（还会被任务栏抢走）。只有 macOS 的 `platform` 才是 ⌘。
* **修法**：在键表层统一收口：`KeyCombo::from_keystroke` 非 macOS 时把 `control` 落到 `cmd` 位、`ctrl` 位置 false；配置里 `cmd+…` 与 `ctrl+…` 在非 macOS 同义。一份配置跨平台可读，Windows 的组合键也真的能用。
* **验证方法**：`VisualTestContext::simulate_keystrokes("ctrl-t")` 直接派发按键，比合成输入（keybd_event + 前台窗口 + 焦点）可靠得多——合成输入那套在本机 RDP 环境下连点侧边栏都要试好几轮。以后要验按键路由，一律走 headless 派发。

## 7. 自定义命令的占位符不能静默变空串

* **风险点**：命令串里的 `{file}` 在没有选中条目时若被替换成空串，`rm {file}` 就成了 `rm`，`wc -l {file}` 变成等标准输入——语义完全变了。
* **做法**：`expand` 返回 `(命令行, 是否可用)`，缺上下文时占位符**原样保留**并让调用方提示「这条命令需要先选中条目」，不执行。
* **另一条边界**：清单目录只认用户自己的配置目录（`<配置>/mo/commands`），绝不扫描正在浏览的目录——否则「打开别人给的文件夹」就等于跑了它带的脚本。

## 8. 扩展系统为什么不是「动态加载代码」

* **决定**：一个扩展 = `<配置目录>/mo/extensions/<id>/manifest.json`，声明若干条命令（复用自定义命令的占位符与执行层），可启停、可按选中项扩展名条件生效。
* **为什么不塞 `.dll`**：Rust 没有稳定 ABI，往已发布的进程里加载第三方本机代码，要么依赖 `#[rustc_private]`、要么要求用户用与主程序**逐字节一致**的工具链重编译；两条路都不可维护，而且把主进程的内存安全交给任意第三方二进制。清单 + 外部程序：进程隔离、崩溃不连坐、任何语言都能写。
* **必须守住的三条**：
  1. 清单只从用户自己的配置目录读，**绝不扫正在浏览的目录**；
  2. 清单里的 `id` 必须等于所在目录名——启停状态是按目录写回清单的，不一致会写错别人的文件；
  3. 展示名带扩展前缀（`扩展名 · 命令名`），否则多个扩展的同名命令在面板里无法区分；命令重名时后加载的直接丢弃并告警。
* **坏输入不许连坐**：一个目录 JSON 写错，只跳过它，其它扩展照常加载。

## 9. 同步引擎：删除只登记、不落地

* **要求**：镜像模式确实需要「删掉目标端多出来的文件」，但删的是用户数据。
* **做法**：引擎的 `apply` 把删除写成**注入的回调**，只负责「登记要删哪些」，
  本模块不出现任何 unlink；应用层拿到清单后走回收站（有进度、可撤销）。
  测试直接断言「回调之后文件必须还在」，把这条性质钉死。
* **踩过的坑**：一开始想在 `spawn_blocking` 里 `block_on` 拿 tokio 锁提交回收站
  操作——blocking 线程里没有 reactor，也不该跨线程抢异步锁。改成
  「blocking 只做文件复制 + 交回待删清单，删除回到异步侧提交」。
* **另一条**：同步必须先 `plan`（只读）再 `apply`。这是全项目唯一会成批改动
  几百个文件的功能，一步算错就是灾难，UI 必须让用户先过目计划。

## 10. 「显示隐藏文件」：判据跟着条目走，开关要同步所有标签页（2026-09-22）

`config.show_hidden` 早就有了，但**过滤没接**——dotfile 恒显示，`.git` /
`node_modules` 铺满列表。接线时三个决定：

- **判据跟着 `ReadDirEntry` 一起交上来**（新增 `hidden` 字段），不是让上层拿路径
  再 stat 一遍。列目录是**热路径**（进目录 / 刷新 / 前进后退 / 列视图切列都会重
  读），两万条的目录多两万次 syscall 就是肉眼可见的停顿。`read_dir_blocking` 里
  那次 `DirEntry::metadata()`（unix 上就是 lstat）顺手把「类型」和 macOS 的
  `UF_HIDDEN` 标记位一起取了，所以这条判据是**免费**的。
- 属性面板的「隐藏」一栏与列表过滤**共用同一套判据**（`is_hidden_with_metadata`）：
  否则会出现「面板说不隐藏、列表里却被过滤掉」这种自相矛盾的显示。
- **过滤必须在建视图之前**（`load_path` 里 `set_entries` 之前）：`visible_count` /
  分页 / 索引全按视图算，过滤晚了状态栏条数与滚动条长度就会对不上。

两个容易漏的连带处：

- **监听增量**：`WatcherEvent::Created` 也要过滤，否则「显示隐藏文件」关着时，
  终端里 `touch .foo` 一下列表就冒出一条（`entry_at` 只按名字判，够用）。
- **索引爬取**：`mo_search::crawl` 多了 `skip_hidden` 参数。**列表里看不到的，搜索
  也不该搜得到**，顺带 `.git` / `node_modules` 整棵子树不进索引，体积小一个数量级。

⚠️ **开关要同步所有标签页**：它在 `AppState` 里是进程内镜像（`Arc<AtomicBool>`，
热路径不能每次读盘），而每个标签页各持一份 `AppState`——只改当前那份就会「切到
另一个标签页又变回去」。所以 `RootView::toggle_hidden` 拿 `all_apps()` 逐个 set，
并且**切完立刻 `refresh()`**（不重读界面上什么都没变，用户只会以为按键坏了）。

入口：命令面板「显示 / 隐藏隐藏文件」+ 快捷键 `view.hidden`（默认 `cmd+shift+.`，
访达同款）。守卫 `mo-app/tests/hidden_files.rs` 两条（主列表 / 列视图），反向验证：
去掉 `load_path` 的 `.filter(..)` → 变红。

## 11. 主题槽位在测试下必须每线程一份（2026-09-22）

`theme_picker_previews_and_restores` 偶发红：「全局调色板应跟随预览项」，单独重跑必过。

根因：调色板是**进程级静态**（`OnceLock<Mutex<Palette>>`），而 `cargo test` 默认并行、
每条用例都会创建 `RootView`（`RootView::new` 里 `theme::set`）。于是 A 用例刚把调色板
预览成深色，B 用例建 `RootView` 又把它设回浅色，A 的断言就随机落空。

修法：`theme` 的槽位在 `#[cfg(test)]` 下改成 `thread_local`，生产路径照旧（界面只在
主线程跑，写调色板的只有 `RootView::new` 与 `repaint_theme` 两处）。**不要**为了修测试
去动生产语义——`cfg` 分开就两边都不冒险。
